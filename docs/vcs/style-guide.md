# Стайл-гайд

## 1. Коммиты (Conventional Commits + ID задачи)

### Базовый формат

```
<префикс-задачи> <type>(optional-scope): <краткое описание в повелительном наклонении>

<body — что и почему изменено (опционально)>
<footer — ссылки, BREAKING CHANGE, задачи (опционально)>
```

### Префикс задачи

**&lt;ID&gt;** — для удобной связи с YouTrack, добавляем в начало каждого коммита.

Примеры:

- `ELP-10`
- `ELP-11`

### Допустимые типы (только в нижнем регистре)

| Тип        | Описание                                               |
| ---------- | ------------------------------------------------------ |
| `init`     | Старт проекта/таски                                    |
| `feat`     | Добавлена новая функциональность по ТЗ                 |
| `fix`      | Исправлена ошибка ранее реализованной функциональности |
| `refactor` | Перестановки/удаления/чистка без изменения поведения   |

### Как описывать

Пишите, что именно сделано:

- «добавлен функционал корзины»
- «исправлен тип данных в модели пользователя»
- «переименован файл настроек»

### Примеры коммитов

```
ELP-10 feat: добавлены страницы архива и главной с мероприятиями команды
ELP-11 fix: исправлен тип IUser
```

## 2. Merge Request (MR): заголовок и описание

### Цель

Повысить читаемость и ускорить code review.

### Правила

- В название MR включаем идентификатор задачи из YouTrack
- В описании — коротко «что сделано»

### Шаблоны

**Заголовок:**

```
Feature/<ID>
```

**Описание:**

```
Краткая сущность изменений.
```

### Примеры

```
Feature/ELP-11
Рефакторинг модуля отправки email-уведомлений
```

```
Feature/ELP-12
Добавлен функционал создания мероприятий
```

### Рекомендуемый шаблон описания MR

```markdown
## Что сделано

- ...

## Мотивация/контекст

- ...

## Как проверить

1. ...
2. ...

## Регрессии/риски

- ...

## Прочее

- Ссылка на задачу: <YouTrack URL>
```

## 3. Импорты: относительные внутри модуля, абсолютные — между модулями

### Правило

- **Относительные импорты** — используем внутри одной функциональной единицы (`src/features/*`, `src/pages/*` и т. п.): `./`, `../`
- **Абсолютные импорты** — для межмодульных ссылок (из фичи в shared-слой, со страницы на другую и т. п.)

### Примеры

```typescript
// внутри src/features/cart/*
import { CartItem } from "./ui/CartItem";
import { useCart } from "../model/useCart";

// из src/features/cart в shared
import { formatPrice } from "shared/lib/formatPrice";
```

## 4. Комментарии в коде (общие принципы)

### Базовые правила

- ❌ Комментарии не заменяют хороший код — если «творится непонятно что», переработайте код
- ❌ Не описывайте очевидное; комментируйте сложные или потенциально непонятные места
- ❌ Избыточные комментарии ухудшают читаемость
- ✅ Взяли кусок кода из источника — оставьте ссылку рядом
- ✅ Для документирования используем **JSDoc**

### Пример хорошего комментария

```typescript
/**
 * Возвращает кэшируемый список мероприятий.
 * Кэш инвалидации привязан к userId, чтобы исключить утечки между аккаунтами.
 */
export function useEvents(userId: string) {
  // ...
}
```

### Антипаттерны

- ❌ Не оставляем закомментированный код — это снижает читаемость, создаёт избыточность, вводит в заблуждение и устаревает
- ✅ Удаляйте мёртвый код без сожаления

## 5. Кастомные хуки: вынос сложной логики из компонентов

### Правило

Если логики в компоненте > ~20 строк, вынесите её в кастомный хук.

**Хук** — функция с префиксом `use*`, инкапсулирующая состояние, эффекты и пр., чтобы:

- Переиспользовать логику
- Скрыть детали реализации
- Упростить компоненты

### Пример

```typescript
// useProfileUserData.ts
export function useProfileUserData(userId: string) {
  // состояние, эффекты, фетч — всё здесь
  // компонент остаётся «тонким»
}
```

## 6. Нейминг и соглашения по файлам/стилям

### Соглашения по именованию `frontend`

| Что                    | Формат                    | Пример                      |
| ---------------------- | ------------------------- | --------------------------- |
| Папки                  | `kebab-case`              | `profile-user-data`         |
| UI-компоненты (`.tsx`) | `PascalCase`              | `ProfileUserData.tsx`       |
| Логика/утилиты (`.ts`) | `camelCase`               | `useProfileUserDataTabs.ts` |
| Стили модуля           | `<Component>.module.scss` | `HomePage.module.scss`      |
| Пропсы компонента      | `<Component>Props`        | `AvatarUploaderProps`       |
| CSS-классы             | `snake_case`              | `.person_card`              |

### Соглашения по именованию `backend`

| Что                     | Формат                         | Пример                                 |
| ----------------------- | ------------------------------ | -------------------------------------- |
| Папки                   | `kebab-case`                   | `profile-user-data`, `auth-service`    |
| Классы/Сущности (`.ts`) | `PascalCase`                   | `UserController.ts`, `AuthService.ts`  |
| Функции/методы (`.ts`)  | `camelCase`                    | `getUserById()`, `validateEmail()`     |
| Переменные              | `camelCase`                    | `userData`, `isAuthenticated`          |
| Константы               | `UPPER_SNAKE_CASE`             | `MAX_LOGIN_ATTEMPTS`, `API_TIMEOUT`    |
| Переменные окружения    | `UPPER_SNAKE_CASE`             | `.env`: `DATABASE_URL`, `JWT_SECRET`   |
| DB таблицы              | `snake_case` (множ. число)     | `users`, `user_profiles`               |
| DB столбцы              | `snake_case`                   | `created_at`, `user_id`                |
| API маршруты            | `/kebab-case`                  | `/api/user-profiles`, `/auth/sign-up`  |
| Интерфейсы/Типы         | `PascalCase`                   | `IUser`, `CreateUserDTO`               |
| DTO/Schemas             | `<Name>DTO` или `<Name>Schema` | `CreateUserDTO`, `UpdateProfileSchema` |

## 7. Быстрые чек-листы

### Перед коммитом

- [ ] Есть `<ID>` в начале сообщения?
- [ ] Выбран корректный type (init/feat/fix/refactor)?
- [ ] Короткое и чёткое описание (повелительное наклонение)?
- [ ] Нет закомментированного кода?
- [ ] Добавлены ссылки на источники/обоснования при необходимости?

### Перед MR

- [ ] Заголовок `Feature/<ID>`?
- [ ] Краткое описание «что сделано»?
- [ ] Инструкции «как проверить»?
- [ ] Указана ссылка на задачу в YouTrack?
- [ ] Нет «лишних» диффов (форматирование/мусорные файлы)?
